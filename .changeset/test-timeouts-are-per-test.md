The test suite no longer sets a global timeout, and its one repeated start-up tax is gone: the PHI-scanner sweep was paying a `tsx` cold start at twenty separate call sites, and spawning `node` instead roughly halved that file.

Development tooling only: `vitest.config.ts` and the test suite. No source file, no build output and no part of the package's public surface is touched, and nothing here ships in a tarball.

**The trim.** `test/scripts/phi-scan.test.ts` spawns the scanner at twenty call sites, and the cost of each spawn was start-up, not scanning — the fixtures are a few hundred bytes. Measured on a 12-CPU cgroup quota, warmed runs of each against the same scanner and argv: a `tsx` start had a median around **470–500 ms** against **141–200 ms** for `node` running the same TypeScript through its native type stripping, so roughly 300 ms per spawn. That roughly halved the file — a plain base run measured **13,925 ms** across 21 cases, and plain runs after the change measured **5,657 ms and 6,853 ms** across 22. Both runners were checked to produce byte-identical stdout and stderr and the same exit code on a clean file and on a violator before the change, which matters because several cases assert on stderr exactly.

**What the trim costs, and how it is paid.** `pnpm phi-scan` — the script the commit hook and CI actually invoke — still runs `tsx`, so one case still spawns it and asserts that both runners agree on exit code, stdout and stderr. That is a parity assertion rather than a smoke test: if the two ever diverge, it reds instead of the sweep quietly testing something the gate does not run. Node's type stripping is on by default from **22.18** while `engines.node` here is `>=22.0.0`; CI runs the 22 + 24 matrix and both resolve above that, so CI is unaffected, but a developer on 22.0–22.17 would need a newer 22 to run the suite.

**The global timeout.** `testTimeout: 10_000` and `hookTimeout: 10_000` were literals in `vitest.config.ts`; the shared `@cosyte/vitest-config` sets no timeout at all. A global timeout is an assertion about the machine rather than the code — sized for the slowest test in the repo, then inherited by every other test, so a genuinely hung fast test looks merely slow instead of broken. Both are removed. `hookTimeout` was pure noise: Vitest's default hook timeout is **exactly** 10,000 ms, so the literal restated the default. Both defaults were established by measuring a deliberately over-running test and hook, not by reading the documentation.

**Per-test, never global.** Every test whose cost is not fixed now declares its own budget next to the work it does. The cases in `test/scripts/attw-gate.test.ts` that run a real `npm pack` through `attw` have carried an explicit 60 s one all along; three groups were added — the two 200,000-row bulk cases in `test/rxnorm/term-types.test.ts`, the single `tsx`-parity case, and **all of `test/property/**`**, whose runtime varies with the fast-check draw as well as with the box, since this package pins no seed by design. With those declared, every remaining test peaked at **689 ms**, a ~7x margin against the 5 s Vitest default the config now inherits.

**The method is part of the claim.** Ten full runs on a genuinely contended box — a 12-CPU cgroup quota with a fourteen-worker fleet running — of which **six were `vitest run --coverage`**. That is not optional: CI gates on `pnpm test` *and* `pnpm test:coverage`, and the instrumented run is materially slower, roughly doubling the property-suite peaks. An earlier draft of this change measured only the plain run, recorded 499 ms, and was refuted for it.

**Measure before bounding, in both directions.** The argument-refusal cases in `attw-gate` look like they belong with the slow ones and do not: the wrapper rejects the flag before it ever invokes `attw`, so they run no `npm pack` and finish in ~200 ms. And the case that actually came closest to the old ceiling — 9,318 ms against 10,000 ms under load, a 682 ms margin on correct code — was one of the `attw` cases that already had its own 60 s budget, so the global was never what stood between it and a false red.

**What this does not do.** It does not make the suite faster by doing less: the trim removes a fixed start-up cost, not a test, and the case count went up by one. It does not touch `scripts/phi-scan.ts` or `scripts/attw.mjs`, whose behaviour is unchanged. It does not address the `attw` cases' own cost — a real `npm pack` runs about 1,550 ms and that is genuine work, not a tax, so it is bounded rather than trimmed. And the timings here describe one box on one day; they are recorded so the next reader re-measures rather than inherits them.
